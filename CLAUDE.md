# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VIctory runs an Xbox Series X|S title natively on Windows. The console
executable is x86-64 PE32+ built for Zen 2, so its machine code runs **unchanged inside our
process**; VIctory supplies the platform underneath (system APIs, D3D12.X → host D3D12, console
GPU shaders → DXIL) and converts the title's data. See `README.md` for current status and
`docs/architecture.md` for the full picture.

## Rule #1: the asset policy (read `docs/asset-policy.md`)

Nothing from the game (or any other proprietary title) may ever enter the repo, in any form:
assets, executable bytes/strings/tables, disassembly, shader dumps, screenshots, snapshots, or
anything derived from them. Allowed: our own format code, build identities (BLAKE3, CodeView
GUID/age), per-build hook offsets under our own names, byte-pattern signatures, small
interop constants we write, and synthetic test data generated by our code.

- `cargo xtask policy` (pre-commit hook) is an allowlist: allowed file types, < 512 KiB, no
  binary data/signatures, no long hex/base64 runs. Exceptions live in `xtask/src/policy.rs`
  with a reason. The only binary exception is `crates/victory-formats/src/bcpack-tables.bin`.
- Code that writes derived data must call `victory_core::ensure_outside_repo` (the
  `.victory-root` marker defines the tree it refuses to write into).
- Tests needing real files are `#[ignore = "needs …"]` and read paths from env vars, so
  `cargo test --workspace` never needs them; they assert on properties, never snapshots.

## Commands

Toolchain is pinned in `rust-toolchain.toml` (target `x86_64-pc-windows-msvc`). Much of the
loader/HLE/GPU code is `#[cfg(windows)]`; running the title requires Windows.

```powershell
cargo xtask install-hooks                 # sets core.hooksPath=.githooks (runs `cargo xtask policy --staged`)
cargo xtask policy                        # asset-policy check over the tree
cargo test --workspace                    # needs no game data
cargo test -p victory-shader <name>       # single crate / test filter
cargo clippy --workspace --all-targets
cargo fmt --all                           # max_width = 100
cargo run -p victory -- config            # check configured paths (victory.toml, git-ignored)
cargo build --release -p victory
target\release\victory.exe run <game dir>\<exe> --execute
cargo build --profile diag -p victory --features diagnostics   # target\diag\victory.exe, debugging aids
```

Other CLI subcommands (`inspect`, `census`, `lib-exports`, `shader-info`, `translate`) are listed
in `README.md`; `victory translate [--validate]` runs shaders through the translator and reports
what it can't handle yet. `victory census` shows import classification without running anything.

Config: copy `victory.example.toml` → `victory.toml`; all paths must be outside the repo. Env vars
(`VICTORY_GAME_DIR`, `VICTORY_CACHE_DIR`, `VICTORY_DATA_DIR`, `VICTORY_TEST_TITLES`,
`VICTORY_CONFIG`) override it. Logging: `VICTORY_LOG=victory_loader=trace,info`. Debug env
switches (`VICTORY_D3D12_DEBUG`, `VICTORY_D3D12_WARP`, `VICTORY_CAPTURE`, …) only work in the
`diagnostics` build — see the table in `README.md`. Crashes and GPU failures go to `crashes.log`
in the data folder.

`tests/fixtures/hle-probe` is a standalone crate (excluded from the workspace) acting as a
stand-in "title"; `crates/victory-loader/tests/load_probe.rs` builds it into `target/fixtures`
and runs the full prepare/load/bind path on Windows.

## Architecture

Crate flow: game assets → `victory-pipeline` + `victory-game` (using `victory-formats`,
`victory-shader`) → `cache_dir`; game executable → `victory-loader` → native title code →
imports into `victory-hle` → D3D12.X into `victory-gpu` → host D3D12, with shaders translated by
`victory-shader` at pipeline creation. Everything except `victory-game` is platform-level and
testable with any Xbox Series title; title-specific formats and build identities belong only
in `victory-game`; per-build code hooks live in `victory-loader`.

**Loader** (`victory-loader`): patches a copy of the image to look like a DLL (no entry point,
no import directory, TLS callbacks detached) so the Windows loader maps/relocates it and
registers unwind tables without running code; maps title-shipped DLLs the same way; binds every
import itself; then runs TLS callbacks and entry points. Static TLS slot 0 loads are redirected
(`tls.rs`); `crash.rs` reports faults as `module+rva`.

**Import resolution** for each `dll!function`, in order:
1. our implementation in `victory-hle::modules` (always wins);
2. the host function, if `HostPolicy` allows that DLL;
3. an export of a DLL shipped beside the title;
4. a generated stub naming the import (`--unimplemented trap|zero`).

`LoadLibrary`/`GetProcAddress` follow the same rules (console-only DLLs like `xgameruntime.dll`
return pseudo handles). `QueryApiImpl` hands out runtime objects by provider/interface id; online
areas answer as an offline console. `victory-hle::modules::files` rewrites console virtual-drive
paths to host folders (saves live under `VICTORY_DATA_DIR`).

**GPU** (`victory-gpu`): console command lists are kept with zero inline limits so every command
arrives as a call and is replayed on host D3D12. Title GPU addresses are CPU addresses (unified
memory); only changed title memory is copied. Module docs in `lib.rs` map each D3D12.X object to
its file.

**Shaders** (`victory-shader`): containers are DXBC whose DXIL part may carry Xbox `XDAT` blobs
including zlib-compressed GFX10 machine code, which is what gets translated. Pipeline:
`ir::build` (SSA, one instruction per machine instruction) → `structure` (removes EXEC: lane
masks become per-lane booleans/branches) → `resource` (traces descriptors/scalar loads to root
parameters) → `emit` (DXIL). Translation happens when the title creates a pipeline, from the
bytes it passes; ahead-of-time translation is only a warm-up. Results are cached on disk.

**Pipeline** (`victory-pipeline`): a `Converter` is deterministic bytes-in/bytes-out; results go
in a content-addressed cache keyed by converter id, version, and input bytes — bump the
converter version when output changes.

## Conventions

See `docs/code-standards.md` for code standards, `CONTRIBUTING.md` for setup and checks,
and `GLOSSARY.md` for domain vocabulary.

- Known approximations are marked `// shortcut:` (never TODO or FIXME).
- Workspace lints: `unsafe_op_in_unsafe_fn` and `unused_must_use` deny; clippy `all` and
  `undocumented_unsafe_blocks` warn — every `unsafe` block needs a `// SAFETY:` comment.
- Commit subjects are usually prefixed with the area (`GPU:`, `Shaders:`, `loader:`, `xmem:`) and describe the behaviour change in a sentence.
